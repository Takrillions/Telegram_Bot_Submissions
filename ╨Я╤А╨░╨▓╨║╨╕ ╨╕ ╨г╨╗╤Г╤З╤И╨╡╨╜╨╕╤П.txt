Правки и улучшения Telegram-бота предложки

1. Меню команд через "/" с учетом контекста и роли.
Команды должны работать как в личном чате с ботом, так и в супергруппе. При вводе "/" Telegram должен показывать список доступных пользователю команд с кратким описанием каждой. Набор команд зависит от роли: обычный пользователь, администратор или главный администратор.
В супергруппе всплывающее меню команд должно отображаться только в теме General. В отдельных ветках подписчиков список команд через "/" не показывать, чтобы он не мешал переписке. При этом разрешенные команды в ветках могут продолжать работать, если администратор введет их вручную.

2. Разграничение прав администраторов.
Команды разделить минимум на три уровня: обычные, административные и системные/продвинутые. Обычные администраторы супергруппы могут пользоваться только разрешенными административными командами. Полный доступ имеет только главный администратор.
Главный администратор — пользователь, который выполнил первоначальную привязку бота к супергруппе и на момент выполнения системной команды остается ее администратором/владельцем, а бот имеет необходимые администраторские права. Если условия не соблюдаются, пользователь не считается главным администратором.
При попытке выполнить запрещенную команду бот отвечает: «У вас нет доступа к этой команде.»

3. Часовой пояс.
Убрать отображение часового пояса из /panel как обычного информационного поля, чтобы Asia/Tashkent не выглядел как определенная ботом геолокация владельца.
Часовой пояс оставить внутренней настройкой, необходимой для расписаний, автоочистки и уведомлений. Его изменение должно быть доступно только главному администратору через настройки или отдельную команду.

4. Один подписчик — несколько каналов.
Если пользователь подключен к предложкам нескольких каналов, бот не должен молча отправлять сообщения в последний выбранный канал.
После запуска бота пользователь выбирает, в какой канал он хочет написать, но только если ему доступно больше одной предложки. Если доступен только один канал, этот вопрос не задается.
После выбора бот должен явно показывать, в какую предложку пользователь сейчас пишет, и позволять в любой момент сменить активный канал.

5. Несколько каналов у одного владельца.
Один главный администратор должен иметь возможность подключить к одному экземпляру бота до 5 своих каналов/супергрупп одновременно.
Каждая привязка должна быть отдельной сущностью со своими группой, названием, настройками, периодом очистки, часовым поясом, подписчиками, ветками и статистикой.
Если у владельца больше одного канала, в /panel сначала должен отображаться выбор канала, которым он хочет управлять.

6. Анонимный режим подписчика.
После запуска бота и выбора канала бот должен спросить пользователя, хочет ли он отправлять сообщения анонимно или с раскрытием своей личности.
Если пользователь подключен только к одному каналу, выбор канала пропускается, после чего сразу задается вопрос об анонимности.
Бот должен сообщить, что выбранный режим сохраняется и не будет спрашиваться перед каждым сообщением. Также бот показывает команду, с помощью которой пользователь может в любой момент изменить режим приватности.
Если выбран анонимный режим, все последующие сообщения пользователя в текущей предложке отправляются администраторам анонимно до тех пор, пока пользователь сам не сменит режим.
Если пользователь выбрал неанонимный режим, администраторам доступны обычные данные подписчика в соответствии с настройками бота.
При смене режима приватности для этого же пользователя должна создаваться отдельная ветка. То есть анонимная и неанонимная переписка одного пользователя никогда не должны смешиваться в одной ветке.
Режим приватности хранится отдельно для каждой предложки. Пользователь может быть анонимным в одном канале и неанонимным в другом.
В анонимной ветке администраторам не должны показываться имя, username, Telegram ID и иные данные, позволяющие напрямую идентифицировать пользователя. Для внутренней технической связи можно использовать скрытый внутренний идентификатор, который не отображается администраторам.

7. Статистика по каждой предложке.
Добавить раздел /stats или кнопку «Статистика» в /panel.
Минимальный набор показателей:
— всего уникальных подписчиков;
— активных за сутки, 7 дней и 30 дней;
— новых подписчиков за выбранный период;
— общее количество сообщений;
— количество текстовых сообщений;
— количество фотографий;
— количество видео;
— количество голосовых сообщений;
— количество документов;
— количество альбомов;
— количество ответов администрации;
— среднее количество сообщений на пользователя;
— среднее время ответа администрации;
— медианное время ответа;
— доля сообщений/обращений, на которые был получен ответ.

8. Топ активных подписчиков.
Показывать топ-5 пользователей за выбранный период по количеству сообщений.
Желательно отдельно считать количество сообщений, количество дней активности и дату последней активности, чтобы один массовый всплеск сообщений за один день не полностью искажал статистику.
Для анонимных пользователей в статистике использовать нейтральный внутренний псевдоним или номер, не раскрывающий личность.

9. Аналитика активности по времени.
Показывать наиболее активные часы суток и дни недели.
Например: «Пик активности: 19:00–22:00».
Также можно показывать распределение сообщений по часам и среднее количество обращений в сутки.

10. Статистика работы администраторов.
Если в супергруппе несколько администраторов, считать:
— кто сколько дал ответов;
— среднее время первого ответа каждого администратора;
— количество обработанных веток;
— количество обращений без ответа.
Для небольших групп эту функцию можно отключать.

11. Статусы обращений.
Добавить для веток состояния:
— Новое;
— В работе;
— Отвечено;
— Закрыто.
Новая ветка автоматически получает статус «Новое».
После первого ответа администратора статус может автоматически меняться на «Отвечено».
Администратор может вручную перевести ветку в «В работе» или «Закрыто».

12. Защита от случайной автоочистки.
Ветки со статусом «В работе», закрепленные ветки или ветки, которые администратор отметил как важные, не должны автоматически удаляться.
Перед ручной массовой очисткой желательно показывать количество веток, которые будут удалены, и запрашивать подтверждение.

13. Гибкие правила автоочистки для каждого канала.
Помимо текущего количества дней добавить варианты:
— удалить через N дней после последней активности;
— удалить только отвеченные/закрытые ветки;
— закрывать вместо удаления;
— сначала закрывать/архивировать, а окончательно удалять еще через N дней;
— никогда не трогать ветки со специальной отметкой;
— отдельные настройки для каждого подключенного канала.

14. Настройки через кнопки, а не только команды.
Постепенно превратить /panel в нормальную административную панель внутри Telegram.
Пример разделов:
— Канал;
— Статистика;
— Автоочистка;
— Уведомления;
— Администраторы;
— Подписчики;
— Тексты;
— Часовой пояс.
Команды оставить как быстрый альтернативный способ управления.

15. Настраиваемый формат названия веток.
Главный администратор должен выбирать шаблон названия веток.
Примеры:
— Имя · @username;
— Имя · ID;
— №123 · Имя;
— собственный шаблон из разрешенных переменных.
Для анонимных веток должен использоваться отдельный шаблон, который не раскрывает личность, например:
— Аноним #124;
— Анонимное обращение №124.

16. Карточка подписчика.
В первом сообщении новой неанонимной ветки показывать служебную карточку:
— имя;
— username;
— Telegram ID;
— когда впервые написал;
— количество обращений;
— дата последней активности.
Позже можно добавить внутренние заметки администратора и теги.
В анонимной ветке идентифицирующие данные не показывать. Вместо них отображать только безопасную служебную информацию, например внутренний номер анонимного обращения, количество прошлых анонимных обращений и дату активности без раскрытия личности.

17. Управление конкретным подписчиком прямо из его ветки.
В каждой ветке подписчика любой администратор может вызвать отдельную команду управления пользователем, например /user или /subscriber.
После команды бот показывает сообщение «Что вы хотите сделать с этим подписчиком?» и inline-кнопки, чтобы дальнейшее управление происходило без ввода дополнительных команд через "/".
Доступные действия:
— ограничить частоту сообщений, например одно сообщение раз в 5 / 15 / 30 / 60 минут или свой интервал;
— временный мут;
— временная блокировка;
— постоянная блокировка;
— снять все ограничения;
— предупредить пользователя;
— пометить как спам;
— добавить внутреннюю заметку;
— добавить тег;
— посмотреть историю ограничений;
— посмотреть статистику подписчика.
При установке мута, блокировки, ограничения частоты или предупреждения администратор должен указать причину.
Готовые причины:
— Спам;
— Флуд;
— Оскорбления;
— Нарушение правил;
— Реклама;
— Подозрительная активность;
— Другое.
При выборе «Другое» администратор вводит причину вручную.
Причина сохраняется в журнале модерации. При необходимости администратор может выбрать, показывать эту причину подписчику или оставить ее только для администрации.

18. Автоматическое уведомление подписчика об ограничениях.
Любое административное ограничение автоматически сообщается самому пользователю.
Пример: «Администрация канала ограничила частоту отправки сообщений. Вы сможете отправлять одно сообщение раз в 60 минут.»
Для временного мута или блокировки указывать точное время окончания или оставшийся срок.
Для постоянной блокировки сообщать, что доступ ограничен бессрочно.
Если администратор разрешил показывать причину, она также включается в уведомление.

19. Поведение бота во время действующего ограничения.
Если пользователь пытается написать во время мута, временной блокировки или раньше разрешенного интервала, его сообщение не должно попадать администраторам.
Вместо этого бот напоминает о действующем ограничении.
Примеры:
«Для вас сейчас действует ограничение. Следующее сообщение можно отправить через 43 минуты.»
«Доступ к предложке временно ограничен. Ограничение закончится через 5 ч 27 мин.»
При постоянной блокировке бот сообщает, что доступ к этой предложке заблокирован.

20. Ограничения должны действовать отдельно для каждой предложки.
Если один подписчик пользуется несколькими каналами через этого бота, блокировка, мут, лимит сообщений или другие ограничения в канале A не должны автоматически действовать в канале B.
Ограничения хранятся для пары «подписчик + конкретный канал».

21. Журнал модерации.
Все действия с подписчиками фиксировать в истории:
— кто из администраторов применил действие;
— к какому пользователю;
— в каком канале;
— какое действие;
— причина;
— когда применено;
— срок;
— когда ограничение закончилось или было снято.
Главный администратор должен иметь возможность просматривать историю модерации.

22. Поиск по подписчикам и обращениям.
Для крупной предложки добавить поиск по имени, username, Telegram ID и другим доступным идентификаторам.
Для анонимных обращений поиск не должен раскрывать реальные данные пользователя администраторам.

23. Экспорт статистики.
Главный администратор должен иметь возможность получить CSV/XLSX за выбранный период:
— подписчики;
— количество обращений;
— типы медиа;
— активность;
— время ответа;
— статистика администраторов.
Анонимные пользователи в экспорте должны оставаться анонимными, если экспорт предназначен для обычного административного использования.

24. Резервное копирование базы.
Добавить автоматический ежедневный backup SQLite и хранить несколько последних копий отдельно от основной VM.
Резервные копии должны включать привязки каналов, настройки, подписчиков, ветки, ограничения и другую служебную информацию.

25. Безопасное обновление.
Улучшить текущий автодеплой.
Перед обновлением делать резервную копию базы.
После выкладки проверять, что новая версия бота успешно запустилась.
Если новая версия не запускается, автоматически возвращать предыдущую рабочую версию.

Полное редактирование всех реплик и текстовых шаблонов бота. Владелец должен иметь возможность изменить практически любой текст, который бот отправляет пользователям и администраторам, чтобы полностью стилизовать его под конкретный канал. По умолчанию используются стандартные нейтральные тексты, но для каждого канала их можно переопределить отдельно.

Редактирование выполняется не в супергруппе, а в личном чате с ботом. Владелец вводит специальную команду, например /templates или /messages. Если у владельца подключено несколько каналов, бот сначала предлагает выбрать канал, для которого нужно изменить тексты.

После выбора канала бот показывает список всех доступных реплик и шаблонов. Если их много, одновременно отображаются, например, первые 6 пунктов, а снизу находятся кнопки навигации ← и → для перелистывания страниц.

В список должны входить все основные сообщения бота, например:
— приветствие;
— выбор канала;
— выбор анонимного/неанонимного режима;
— сообщение об успешном подключении;
— сообщение об изменении режима приватности;
— подтверждение отправки;
— сообщение о блокировке;
— сообщение о временном муте;
— сообщение об ограничении частоты отправки;
— предупреждение;
— сообщение о снятии ограничений;
— сообщение о попытке написать во время блокировки;
— сообщение об ошибке;
— сообщение об отсутствии доступа;
— сообщение о недоступности предложки;
— запрос причины;
— уведомление о смене настроек;
— уведомления автоочистки;
— системные уведомления подписчику;
— другие тексты, которые бот показывает в процессе работы.

При выборе конкретной реплики бот сначала должен показать:
— её текущее значение;
— где именно она используется;
— при каком событии она появляется;
— кому она показывается: подписчику, администратору или главному администратору;
— какие переменные в ней можно использовать.

Например, для шаблона блокировки бот может объяснить: «Это сообщение отправляется подписчику сразу после временной блокировки. Можно использовать переменные: {channel}, {reason}, {duration}, {until}.»

После этого владелец может нажать Изменить, отправить новый текст и увидеть предпросмотр. Также должны быть кнопки «Вернуть стандартный текст» и, желательно, «Сбросить все шаблоны канала» с дополнительным подтверждением.

Шаблоны должны поддерживать безопасные переменные, чтобы владелец мог писать, например: Вы временно ограничены в канале {channel}. Причина: {reason}. Осталось: {remaining}. Бот обязан проверять неизвестные переменные и не сохранять шаблон с ошибкой.

Настройки реплик хранятся отдельно для каждого канала. Поэтому один и тот же бот может выглядеть и общаться совершенно по-разному в разных подключенных предложках.

27. Женская персона бота. Бот должен использовать женский род во всех стандартных репликах и системных сообщениях. Формулировки вроде «готова принять сообщение», «я отправила», «я не смогла выполнить действие» и другие фразы с родом должны быть согласованы с женской персоной бота.

Эта настройка применяется ко всем стандартным шаблонам по умолчанию. При этом владелец канала по-прежнему может вручную изменить любую реплику через редактор шаблонов.

28. Возможность полностью отключить автоматическую очистку веток. Для каждого подключённого канала главный администратор должен иметь возможность отдельно включить или выключить автоматическую очистку/удаление веток. По умолчанию может использоваться стандартный период, но владелец должен иметь вариант Автоочистка: выключена. При выключенной автоочистке scheduler не должен удалять, закрывать или архивировать ветки этого канала и не должен отправлять предупреждения о предстоящей очистке. Ручная очистка при этом остаётся доступной. Настройка должна находиться в /panel → Автоочистка и действовать независимо для каждого из подключённых каналов. При повторном включении автоочистки владелец выбирает новый период и политика отсчёта начинается заново от момента включения, чтобы старый просроченный next_reset_at не вызвал мгновенное массовое удаление.

29. Добавь в зафиксированное ТЗ ещё одно обязательное требование: настраиваемые теги анонимных подписчиков.

Для каждого channel_id главный администратор задаёт префикс анонимного пользователя, например «Анон».

Бот автоматически формирует:
Анон-1
Анон-2
Анон-3
...
Анон-18

Требования:

1. Префикс задаётся при первоначальной настройке канала и позже изменяется через /panel.

2. Счётчик отдельный для каждого channel_id.

3. Когда подписчик впервые выбирает anonymous-режим в текущем цикле, ему атомарно присваивается следующий свободный номер.

4. После назначения бот сообщает подписчику:
«Ваш анонимный тег: Анон-18»
с использованием фактического настроенного префикса.

5. Анонимная forum-тема этого пользователя получает такое же название — например «Анон-18».

6. Во всех административных интерфейсах анонимного обращения должен использоваться этот тег вместо имени, username и Telegram ID.

7. Один пользователь сохраняет один и тот же анонимный тег в пределах данного канала и текущего цикла. Повторные сообщения или переключение anonymous → identified → anonymous не должны выдавать новый номер в том же цикле.

8. identified- и anonymous-ветки пользователя по-прежнему являются разными ветками.

9. Изменение префикса не должно автоматически переименовывать уже существующие ветки и выданные теги. Новый префикс применяется к новым назначениям.

10. После полноценного сброса цикла нумерация начинается заново с 1.

11. Если автоматическая очистка отключена, счётчик автоматически не сбрасывается.

12. При ручном полном сбросе/очистке канала должна существовать возможность вместе с ним сбросить анонимную нумерацию.

13. Выдача номера должна быть защищена от гонок: два пользователя, одновременно выбравших анонимность, не должны получить одинаковый номер.

14. Внутренне можно хранить Telegram user_id для маршрутизации сообщений, но он не должен раскрываться администраторам через анонимный тег, карточку, поиск, статистику, экспорт или журнал.

Учти это требование минимум в этапах:
- channel-модели и настроек;
- anonymous/privacy-модели;
- создания и именования тем;
- очистки и циклов;
- /panel.

Сейчас ничего из этого не реализуй. Только включи требование в план, укажи, какие этапы оно затрагивает, и остановись.

30. Главный администратор должен иметь возможность настраивать информационную карточку, которую новый подписчик видит по центру пустого чата с ботом до первого нажатия кнопки «Start».

Карточка должна включать:

изображение либо поддерживаемое Telegram видео/анимацию;
основной текст-описание;
возможность посмотреть предпросмотр перед применением;
возможность заменить медиа или удалить его;
возможность вернуть стандартные текст и медиа.

Редактирование должно выполняться через личный чат с ботом в отдельном разделе настроек, например /panel → Оформление бота → Карточка до Start.

Важное ограничение Telegram: эта карточка относится к профилю самого бота и показывается ещё до выполнения /start. Bot API позволяет менять описание бота, а Telegram также поддерживает изображение/видео для этого блока, но настройки не привязываются к channel_id или deep-link. Поэтому такая карточка является общей для всего экземпляра бота и не может одновременно отличаться для разных подключённых каналов.

После нажатия Start уже должна применяться индивидуальная стилизация конкретного канала: своё приветствие, тексты, выбор анонимности и остальные настраиваемые шаблоны.

31. Массовая рассылка подписчикам через General

В каждой подключённой супергруппе должна быть функция массовой рассылки по существующим веткам подписчиков. Запускать её можно только из темы General соответствующей супергруппы и только главному администратору этого channel_id. Обычные администраторы не должны иметь доступа к запуску, подтверждению или отмене рассылки.

Главный администратор запускает команду рассылки. Бот переводит его в отдельный сценарий и спрашивает, какое сообщение необходимо отправить. За одну рассылку принимается ровно одно Telegram-сообщение. Допустимы поддерживаемые Telegram типы сообщений: обычный текст, фото, видео, документ, аудио, голосовое сообщение, анимация/GIF, стикер, опрос и другие типы, которые бот способен корректно скопировать/переслать. Альбом из нескольких отдельных сообщений не должен случайно приниматься как несколько независимых рассылок; если поддержка альбомов реализуется, он должен обрабатываться как единая публикация.

После получения сообщения бот показывает предварительный просмотр и предлагает действия:

Отправить
Редактировать
Отмена

При выборе «Редактировать» администратор отправляет новое сообщение, которое полностью заменяет предыдущий вариант рассылки. Рассылка не начинается до явного нажатия «Отправить». При «Отмена» состояние полностью очищается и ничего не рассылается.

Получателями являются подписчики конкретного channel_id, которые уже взаимодействовали с предложкой и для которых существует или существовала их пользовательская ветка. Рассылка не должна затрагивать подписчиков других каналов того же владельца.

Рассылка выполняется по реальным пользователям, а не по количеству forum topics. Один Telegram-пользователь должен получить конкретную рассылку не более одного раза, даже если в супергруппе для него существуют одновременно несколько веток, например отдельная anonymous-ветка и identified-ветка.

Если подписчик раньше общался анонимно, затем переключился в публичный режим и для него появилась вторая ветка, система должна определить его текущий актуальный режим/ветку и отправить рассылку только туда. В старую неактуальную ветку копия сообщения не отправляется. Аналогичное правило действует при обратном переключении из публичного режима в анонимный.

При выборе получателя система должна использовать внутреннюю связь channel_id + user_id и текущий privacy/active-topic state. Нельзя строить список получателей простым перебором всех тем супергруппы, иначе один пользователь может получить несколько копий.

Для каждой рассылки должен существовать уникальный broadcast_id и журнал доставки, позволяющий однозначно определить:

broadcast_id + channel_id + user_id

как уже обработанного получателя. Это должно защищать от повторной отправки при повторном callback, перезапуске процесса или частичном повторе операции.

Если актуальная ветка подписчика была удалена, закрыта или недоступна, бот не должен автоматически отправлять сообщение в старую ветку другой privacy-модели. Такой получатель фиксируется как недоставленный либо обрабатывается согласно явно определённой безопасной политике.

После завершения главный администратор должен получить итог рассылки минимум с количеством:

уникальных получателей;
успешно доставленных сообщений;
недоставленных;
пропущенных;
ошибок.

Одна ошибка Telegram при отправке конкретному подписчику не должна останавливать всю рассылку.

Повторное нажатие кнопки «Отправить» не должно запускать второй экземпляр той же рассылки. Одновременно для одного channel_id не должно выполняться несколько конфликтующих массовых рассылок.

Команда должна работать только из General. Попытка запустить её из пользовательской forum-ветки, другой темы, личного чата или чужой супергруппы должна безопасно отклоняться.

Вся функция должна сохранять существующие требования анонимности: массовая рассылка не должна раскрывать главному администратору или другим администраторам соответствие между anonymous и identified ветками одного пользователя. Внутренне Telegram user_id разрешено использовать для дедупликации и маршрутизации, но он не должен появляться в интерфейсе анонимной ветки.

32. Два режима обработки реакций администраторов

Для каждого channel_id должна существовать отдельная настройка режима работы реакций администраторов в пользовательских forum-ветках. Управлять режимом можно только через General соответствующей супергруппы и только главному администратору.

Должны поддерживаться два режима.

Режим 1 — реакции подписчику. Это стандартный режим. Если администратор ставит реакцию на сообщение подписчицы в её forum-ветке, бот определяет соответствующее пользовательское сообщение и уведомляет подписчицу о реакции. Например: «Администратор отреагировал на ваше сообщение: 👍». Сам Telegram автоматически не синхронизирует реакции между сообщением в супергруппе и личным чатом, поэтому это поведение реализуется ботом. Удаление реакции не должно создавать отдельное уведомление. Изменение реакции может обрабатываться как новая реакция согласно общей логике дедупликации.

Режим 2 — реакции как отправка в специальную ветку. В этом режиме реакция администратора больше не уведомляет подписчицу. Вместо этого любая новая реакция администратора на сообщение в любой пользовательской forum-ветке автоматически отправляет исходное сообщение в отдельную служебную ветку этой супергруппы.

При первом включении Режима 2 бот должен спросить главного администратора, как назвать служебную ветку. После ввода названия бот самостоятельно создаёт соответствующий Forum Topic и сохраняет его message_thread_id в настройках конкретного channel_id.

Например:

/panel → Реакции → Режим 2

→ «Как назвать ветку, куда будут отправляться отмеченные реакциями сообщения?»

→ главный администратор вводит: Важное

→ бот создаёт topic Важное

→ после этого реакции администраторов начинают использоваться как механизм отправки сообщений туда.

Главный администратор должен иметь возможность:

переключать Режим 1 / Режим 2;
создать служебную ветку;
изменить её название;
при необходимости выбрать/пересоздать служебную ветку, если старая была удалена;
видеть текущий активный режим.

Обычные администраторы не могут переключать режим, создавать служебную ветку или изменять её настройки. Однако при включённом Режиме 2 любой администратор с доступом к пользовательской ветке может поставить реакцию и тем самым отправить соответствующее сообщение в служебную ветку.

В Режиме 2 бот должен реагировать на новые реакции во всех forum-ветках конкретного channel_id, кроме:

General;
самой служебной ветки для реакций;
других системных веток, если они специально помечены как исключённые.

Служебная ветка обязательно исключается, чтобы реакция на уже перенесённое туда сообщение не создавала цикл повторной отправки.

При реакции бот должен отправлять само исходное сообщение, а не только его текст. Должны корректно обрабатываться:

текст;
фото;
видео;
GIF/анимации;
документы;
голосовые;
аудио;
стикеры;
опросы;
другие поддерживаемые Telegram типы.

Предпочтительно использовать именно пересылку сообщения, если Telegram позволяет её для данного типа сообщения, чтобы вверху пересланного сообщения сохранялось доступное Telegram указание исходного отправителя/источника. Если конкретный тип сообщения нельзя переслать, допускается безопасный fallback через копирование с сохранением доступного содержимого.

Для anonymous-подписчицы пересылка не должна нарушать требования анонимности. Если обычная Telegram-forward операция способна раскрыть её настоящую Telegram-личность, такую пересылку использовать нельзя. В этом случае бот должен применить privacy-safe копирование и отображать только её анонимный тег.

Подписчица не должна получать никаких уведомлений о том, что её сообщение было отправлено в служебную ветку. Она не должна видеть:

факт пересылки;
реакцию-триггер;
название служебной ветки;
администратора, поставившего реакцию.

В Режиме 2 реакция является внутренним административным инструментом.

Обработка должна быть scoped по channel_id: реакция из одного подключённого канала не может отправить сообщение в служебную ветку другого канала того же владельца.

Необходимо предусмотреть дедупликацию reaction updates. Повторная доставка одного и того же Telegram update не должна повторно отправлять сообщение.

Удаление реакции не должно удалять уже отправленное в служебную ветку сообщение и не должно отправлять его повторно.

Если несколько администраторов независимо поставили реакции на одно сообщение, система должна иметь чёткую политику. По умолчанию одно исходное сообщение рекомендуется отправлять в служебную ветку только один раз, независимо от количества последующих реакций, чтобы исключить дубликаты. При этом внутренне можно сохранить информацию о новых реакциях для журнала.

Если служебная ветка была удалена или стала недоступна, бот не должен молча отправлять сообщения в другую тему. Режим 2 должен перейти в состояние, требующее от главного администратора восстановить/пересоздать служебную ветку через General.
